# 工作流：并购重组视频旁白

本文件用于取得或接收画面交易数据和公告文件，再把它们转成面向非专业观众的中文短视频旁白。核心原则是：画面数据已经定义了视频结构，旁白必须跟着画面走。

## 目录

1. 资料取得与确认
2. 项目目录和交付模式
3. 抽取并锁定画面步骤
4. 阅读公告
5. 联网补充资料
6. 建立主体关系卡和概念卡
7. 搭建故事骨架
8. 写分段脚本
9. AI 模拟核稿
10. 润色与检查
11. 最终交付模板

## 1. 资料取得与确认

正式写稿前必须取得两个输入：

- 画面数据：通常是 `标的名称原始数据.txt` 或 `.rtf`。
- 公告文件：通常是公告、报告书、预案或说明书 PDF。

### 路径 A：用户提供资料

用户在当前请求或对话中附上、粘贴或明确指定两个输入时，直接使用。工作区或历史目录里存在同名文件、相似公司文件或唯一候选文件，不视为用户已经指定；不能自行匹配或选择本地文件。

### 路径 B：自动获取资料

用户提供股票代码或要求自动获取时，在项目输出目录运行：

```bash
python3 tools/ma_data_fetch/ma_data_fetch.py fetch-data 300277 \
  --output-dir "项目目录"
```

命令会输出公司简称、案例 ID、首次公告日期、动画页和原始数据路径，并把接口返回的 `data` 对象保存为兼容现有解析器的 `公司简称原始数据.txt`。未传 `--market` 时，工具按原查询说明为沪市 `6` 开头代码选择 `15`，其余代码选择 `17`；如接口规则变化，可手动覆盖。

再使用命令输出的公司简称、股票代码和首次公告日期检索公告候选：

```bash
python3 tools/ma_data_fetch/ma_data_fetch.py find-announcements \
  --code 300277 \
  --company "海联讯" \
  --first-date 2024-10-28
```

检索后必须执行人工确认门禁：

1. 向用户展示每个候选的公告日期、完整标题和 PDF 链接。
2. 明确询问用户使用哪个标题，然后停止当前创作流程。
3. 不得把排序第一名视为用户确认，不得自行下载或读取候选公告。
4. 用户确认完整标题后，才下载对应 PDF：

```bash
python3 tools/ma_data_fetch/ma_data_fetch.py download-announcement \
  --url "https://static.cninfo.com.cn/finalpage/2024-10-28/1221522009.PDF" \
  --title "关于筹划重大资产重组暨停牌公告" \
  --output-dir "项目目录"
```

只有原始数据已生成且公告标题已经用户确认、PDF 已下载，资料门禁才通过。如果用户只给公司名，先索要股票代码；用户明确禁止联网时，只索要缺失的本地资料。没有候选时，可扩大日期窗口或核对首次公告时的公司简称，但仍不得自拟公告。

默认不向用户追问开头噱头方向。开头应从交易事实里生长出来：这次交易为什么发生、解决了什么压力、造成了什么结构变化。

## 2. 项目目录和交付模式

默认模式是在对话中直接交付旁白。即便直接交付，也要先完成资料取得与确认门禁、步骤抽取、资料核对和自检。

默认交付包含视频大标题、分段脚本（含来源核实）、来源清单和纯文案版。视频大标题放在含来源核实版最前面；画面步骤小标题作为分段脚本内部的段落标题出现，不要在文末单独列“小标题”。每个文案段落后必须紧跟 `【画面】`、`【来源】`、`【核实内容】`；`html chart` 段落在 `【画面】` 后还必须紧跟 `【画面数据】`。来源清单之后必须追加纯文案版，纯文案版重新包含相同的视频大标题，保留全部段落小标题和正文，删除画面、画面数据、来源和核实内容。不要输出快节奏版、短版、配音提示、分镜脚本或其他附加栏目，除非用户明确要求。

纯文案版是默认交付的一部分，不再等待用户单独提出。用户明确要求只要含来源核实版或只要纯文案版时，才按其要求删减。

当用户要求文件交付时，创建：

```text
标的名称_并购重组文案_YYYYMMDD/
├── 标的名称并购重组文案.md
├── 正文实际引用的公告1.pdf
└── 正文实际引用的公告2.pdf
```

Markdown 合并含来源核实版、来源清单和纯文案版。把正文实际引用的每份公告复制或下载到同一目录，来源清单使用交付目录内的真实文件名。只有用户明确要求完整核查包时，才额外生成 `交易步骤核对.md`、`资料汇总.md` 和 `AI模拟核稿.md`。快速回答时，不要为了形式额外生成文件。

## 3. 抽取并锁定画面步骤

画面数据是视频顺序的第一依据。

画面数据由用户指定或由自动获取工具生成后，优先运行：

```bash
python3 tools/transaction_data_inspector/transaction_data_inspector.py "标的名称原始数据.txt" --output 交易步骤核对.md
```

脚本失败时，手动抽取同样字段：

| 字段 | 含义 |
|---|---|
| `company_info.name` / `code` | 画面数据中的上市或挂牌公司 |
| `process[].sort` | 步骤顺序 |
| `process[].stage_name` | 步骤小标题候选 |
| `process[].description` | 画面对该步骤的描述 |
| `process[].trade_list` | 该步骤涉及的主体和标的 |
| `assets_info[].status` | 交易前后状态快照 |

建立锁定后的步骤表：

| 顺序 | 画面步骤名 | 画面描述 | 核心动作 | 结果 |
|---|---|---|---|---|

规则：

- 表格行数必须等于画面步骤数量。
- 除明显乱码外，小标题使用 `stage_name`。
- 一个步骤里如果合并了多个名称，例如 `资产置换,增发收购`，保留合并名称。
- `description` 是旁白边界。不要把一个画面步骤拆成多个新段落标题。
- `trade_list` 可用于识别谁给谁、给什么，但看不清的地方必须回到公告核对。

## 4. 阅读公告

公告只回答旁白需要的问题：

1. 谁是上市/挂牌公司？
2. 谁是标的公司或标的资产？
3. 谁是交易对方、出让方、投资方、控股股东和实际控制人？
4. 这次交易为什么发生？
5. 它解决什么问题：融资通道、B 股转 A 股平台、资产质量、同业竞争、控制权归集、业务转型、债务压力、业绩压力，还是国资整合？
6. 交易完成后发生什么变化：控制权、主营业务、资产范围、上市地位、子公司关系、财务体量或业务重心？
7. 哪些数字对理解交易必不可少？

优先检索公告文件中的这些关键词：

- `本次交易的目的`
- `本次交易的背景`
- `交易方案`
- `重大资产置换`
- `发行股份购买资产`
- `换股吸收合并`
- `交易对方`
- `标的资产`
- `置出资产`
- `置入资产`
- `股权结构`
- `控股股东`
- `实际控制人`
- `同业竞争`
- `表决权`
- `业绩承诺`

长公告文件先读目录、交易概述、交易目的和背景、方案概览、交易对方、标的业务、交易前后控制关系。不要把整本报告复述成旁白。

## 5. 联网补充资料

资料门禁通过后，除非用户明确禁止联网，否则必须搜索公开资料。公告、主体名称、上市状态、监管进度和交易背景都可能随时间变化。

资料优先级：

1. 交易所公告页、公司公告页、官方公告文件。
2. 公司官网，用于确认业务身份。
3. 权威财经媒体，用于补充交易背景。
4. 研报只在能帮助理解业务背景或行业地位时使用。

搜索词示例：

- `上市公司名 重大资产重组 背景`
- `上市公司名 标的公司 交易目的`
- `标的公司 主营业务 官网`
- `上市公司名 控股股东 实际控制人`
- `交易简称 财经 新闻`

联网资料只用于补充：

- 交易为什么发生。
- 各家公司到底做什么。
- 某个概念是否需要解释。
- 用户要求最新信息时，核对交易状态或主体名称。

不得用联网资料新增画面数据里没有的交易步骤。
不得用普通网页搜索结果替代画面原始数据，也不得据此自拟视频小标题；自动获取工具生成的结构化原始数据属于正式画面数据输入。

## 6. 建立主体关系卡和概念卡

写稿前先建一个简短主体表：

| 主体 | 角色 | 与其他主体关系 | 首次出现时的自然解释 |
|---|---|---|---|

首次出现写法示例：

- `多喜爱是这次交易里的上市公司，交易前主业是家纺。`
- `浙建集团是被装入上市公司的标的资产，主业是建筑施工和相关工程服务。`
- `浙江省国资运营公司是交易对方之一，也是浙江省国资体系下的平台。`

如果出现专业概念，用一句话翻译：

| 概念 | 通俗解释 |
|---|---|
| 表决权 | 它决定谁能在股东会里主导决策，持股比例和控制力有时并不完全相同。 |
| 控制权 | 必须说清楚是上市公司自身控制权变化，还是上市公司对子公司或标的公司的控制关系变化。 |
| 同业竞争 | 同一个控制人下面有业务重叠的平台，重组通常是为了划清边界或把业务归集到一个平台。 |
| 资产置换 | 两边拿资产包互换，差额部分再用现金或股份补足。 |
| 增发收购 | 上市公司发行新股作为对价，向交易对方购买资产或股权。 |
| 吸收合并 | 一个公司留下来，承接另一个公司的资产、负债、业务、合同和权利义务，被吸收方可能注销。 |

概念解释只在必要时进入旁白，不要把旁白写成术语表。

## 7. 搭建故事骨架

写正文前先回答：

1. 这次交易发生的简短原因是什么？
2. 交易前有什么压力、错配或矛盾？
3. 观众必须先理解哪些主体关系？
4. 画面数据锁定的步骤到底是哪几步？
5. 所有步骤完成后，公司状态发生什么变化？

开头要短，但必须让观众知道要看什么。第一段优先提出来自交易事实的核心问题或矛盾，再进入背景和主体关系。

可用抓手：

- 错配：小上市平台遇到大标的资产，旧业务遇到新业务，融资受限资产进入 A 股平台。
- 问题：同业竞争、亏损资产、控制权争议、融资瓶颈。
- 结构变化：国资整合、控制权归集、资产置换、业务转型。

推荐开头句：

- `一家做医疗耗材的公司，为什么突然要买一家芯片公司？`
- `小体量上市平台，为什么要装进一个更大的资产包？`
- `这笔交易要解决的，不只是买一家公司，还包括上市公司原有业务的增长压力。`

不要用审批流程、日期流水账、公告名称、一串比例或纯业务定义开头。不要为了吸引人使用夸张词、股价暗示或无来源判断。

## 8. 写分段脚本

推荐结构：

```markdown
# 视频大标题

...

# 分段脚本（含来源核实）

## [有叙事功能的开头小标题，例如：跨界悬念 / 主业承压 / 平台错配]
...
【画面】：b-roll素材
【来源】：[1]
【核实内容】：...

## [画面步骤名 1]
...
【画面】：并购重组范式
【来源】：[1] [2]
【核实内容】：...

## [画面步骤名 2]
...
【画面】：并购重组范式
【来源】：[1] [2]
【核实内容】：...

## [有叙事功能的结尾小标题，例如：双主业转型 / 整合考验 / 新旧业务并行]
...
【画面】：b-roll素材
【来源】：[2] [3]
【核实内容】：...
```

写作规则：

- 一个开场段、每个画面步骤至少一个段落、最后一个收束段。开头必须先提出核心问题或矛盾，再解释主体和背景；不能让观众听完第一句还不知道要看什么。
- 每个文案段落必须包含 `【画面】`、`【来源】`、`【核实内容】` 三项；来源不要只堆在文末。`html chart` 段落还必须在 `【画面】` 后立即包含 `【画面数据】`。
- 将核心问题、原因解释、业务介绍和主体关系与数据句拆开。前者使用 `白板` 或 `b-roll素材`；后者只有在数据完整且能直接制作图表时才使用 `html chart`。
- `【画面数据】` 优先用 Markdown 表格列出主体、指标、期间、数值和单位。多主体比较必须给出每个主体的同口径分项；只有合计数时先补数，无法补齐就改用 `白板` 或 `b-roll素材`。
- 开头和结尾小标题必须像 `跨界悬念`、`主业承压`、`平台错配`、`整合考验` 一样有叙事功能，不得写成 `开场：交易为什么发生`、`收束：交易完成后` 这类模板占位标题。
- 每个步骤只讲：谁做动作、什么资产/股权/权利/股份/现金发生移动、从谁到谁、用什么对价、结果是什么。
- 如果画面数据把多个法律动作合成一步，旁白也按一步讲。
- 主体关系先交代，再讲交易动作。
- 句子要短，适合口播。
- 数字只保留能解释动作、规模、控制关系或交易前后变化的部分。
- 已经讲过的步骤，不要换一种说法再解释一遍。
- 避免 `对应到画面里`、`先把关系讲清楚`、`这不是……而是……`、反复使用 `简单来说` 等解释腔。
- 避免 `最值得看`、`最核心`、`最关键`、`真正改变的是`、`真正要看的是` 等绝对化表达。需要强调时，改成 `要看的是`、`需要关注的是`、`这一步改变的是`。
- 避免 `画面数据里`、`画面显示`、`视频里`、`对应画面` 这类制作视角表达。正文直接说交易动作，例如 `这次交易集中在一个步骤`，不要说 `画面数据里，这次交易集中在一个步骤`。
- 避免 `公司解释`、`资料显示` 这类模糊来源表达。需要归因时点名具体来源，例如 `业绩预告中提到`、`停牌公告披露`、`年报显示`、`证券时报报道`。
- 不机械朗读风险因素、审批条件、停复牌或不确定性提示。

字数建议：

- 默认主版：700-1200 个汉字，适合 60-120 秒视频。
- 画面步骤超过 5 个时，可放宽到 1500 字左右，但每一步仍要克制。
- 用户要求 30-45 秒版本时，优先压缩开头和结尾，不牺牲步骤准确性。

## 9. AI 模拟核稿

交付前，以 AI 模拟并购重组编辑或法律财务核稿视角检查。不得暗示真实专家已经审阅或背书。

核稿表：

| 检查项 | 通过/需修改 | 说明 |
|---|---|---|
| 步骤数量和顺序是否与画面数据一致 |  |  |
| 是否没有新增交易步骤 |  |  |
| 关键主体是否在交易动作前交代清楚 |  |  |
| 交易目的是否清楚且不过度展开 |  |  |
| 控制权、表决权、同业竞争等概念是否必要且通俗 |  |  |
| 数字是否必要，没有堆砌 |  |  |
| 是否没有无关流程性内容 |  |  |
| 结尾是否描述状态变化，没有口号化 |  |  |

只要有一项不通过，先改稿再交付。

## 10. 润色与检查

事实和步骤检查通过后，才能做风格润色。

生成本地 Markdown 分段脚本时运行：

```bash
python3 tools/narration_lint/narration_lint.py "并购重组分段脚本.md"
```

若检查发现缺少必要栏目或出现不宜表达，除非该词只出现在用户原始要求或引用材料中，否则应修改正文。

## 11. 最终交付模板

### 对话直接交付

```markdown
# 视频大标题

[客观、严谨、新闻标题式]

## 分段脚本（含来源核实）

[分段文案。每段文案后必须紧跟 `【画面】`、`【来源】`、`【核实内容】`。`html chart` 段落必须在 `【画面】` 后紧跟 `【画面数据】`。画面步骤小标题以二级或三级标题嵌入正文，例如 `## 资产置换`、`## 增发收购`。]

---

## 来源

[编号、来源标题、链接或路径、核实用途]

---

# 纯文案版

## 视频大标题

[与含来源核实版相同的视频大标题]

## [与分段脚本相同的小标题]

[只保留正文]
```

默认附来源清单，并在来源之后追加带完整大小标题的纯文案版；不在文末单独列小标题，不输出快节奏版或配音提示。若存在重要差异，增加简短 `核对说明`。

错误示例：
```markdown
## 视频大标题和小标题
大标题：...
小标题：步骤1 / 步骤2 / 步骤3
```

### `交易步骤核对.md`

```markdown
# 交易步骤核对

- 画面数据文件：
- 公告文件：
- 上市/挂牌公司：
- 画面步骤数量：

| 顺序 | 画面步骤名 | 画面描述 | 核心动作 | 结果 |
|---|---|---|---|---|

## 公告与画面差异

| 差异点 | 画面数据 | 公告信息 | 处理方式 |
|---|---|---|---|
```

